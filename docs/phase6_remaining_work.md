remains is a set of individually-documented deferred fields (each needs
either a physical modelling decision or new infrastructure this codebase
doesn't have yet) plus a couple of known follow-up items. This supersedes
the stale "not started" language for 6b/6c in
[DEVELOPMENT.md](../DEVELOPMENT.md) and
[master_catalogue.md](master_catalogue.md) — those should be updated to
point here rather than re-describing status inline.

## 6a/6b/6c — implemented

- **`schema.py`**: `CatalogueSchema`/`FieldSpec`, YAML I/O, `default_schema()`.
- **`api/catalogue.py`**: `CatalogueDataset` (read-side adapter, `kind="satellites"`).
- **`pipeline.py`**: `HaloExtractStage`, `TreeExtractStage`, `CrossMatchStage`,
  `QualityControlStage`, `WriteStage`, `CatalogueBuilder`
  (`_load_config`/`run`/`run_from_stage`), `HostJob`,
  `_concatenate_contexts` (multi-host row-stacking + global `SatelliteID`
  renumbering).
- **`derived.py`**: `HaloPropertiesStage`, `OrbitalPropertiesStage`,
  `StarFormationHistoryStage`, `HostEnvironmentStage`, `EnvironmentStage`,
  `ObservabilityStage`, `DorchaSpecificStage` (partial — see deferred
  fields below).
- **`backends.py`**: `SharkGalaxyBackend` (including optional FSPS
  photometry, see below) and `HydroGalaxyBackend`, both with
  `galaxy_properties()`/`star_formation_history()`/
  `native_comoving_little_h()`; shared helpers `rebin_sfh()`,
  `_cosmic_time_gyr()`.
- **`validation.py`**: `ValidationIssue`/`ValidationReport` (incl.
  `to_json()`), `SchemaValidator`, `IntegrityValidator`, `PhysicalValidator`.
- **`webreport.py`**: `FigureSpec`, `WebReport` (incl. `build()`).

`ExtractStage` itself (the base class) is deliberately left abstract
(`NotImplementedError`) — only its two concrete subclasses
(`HaloExtractStage`/`TreeExtractStage`) are meant to be instantiated;
particle tagging/selection-function/Rubin-detectability extraction would
each be a new subclass, not an implementation of the base class itself.

### FSPS photometry (`SharkGalaxyBackend`)

`compute_photometry=True` (constructor kwarg, default `False`) adds
`LuminosityV`/`Luminosity_ugriz`/`AbsoluteMagnitude_ugriz` via
`shark.photometry.PhotometryPipeline` — real FSPS SSP convolution against
each satellite's matched SHARK galaxy's SFH. Off by default: it needs
python-fsps installed with its SSP template data (`SPS_HOME`), and is
orders of magnitude slower per galaxy than every other field. One
`PhotometryPipeline` (i.e. one FSPS `StellarPopulation`) is built per
(model, z_obs) and cached/reused across every satellite in a build — see
`SharkGalaxyBackend._photometry_pipeline_for`. `HalfLightRadius` is still
**not** computed even with photometry on — FSPS gives an SED (a
luminosity), not a spatial light profile, so a light radius still needs
an assumed structural model. `HydroGalaxyBackend` has no photometry path
at all (would need its own SPS convolution over star particle ages/
metallicities/masses — not attempted here).

## 6b — deferred fields (per stage, with reason)

Each item below was deliberately **not** invented — implementing it
requires either an explicit modelling choice the caller must supply, or
infrastructure that doesn't exist yet. Full reasoning lives in the
docstring of each stage in `derived.py`/`backends.py`; this is a
condensed index.

### `HostEnvironmentStage` / `EnvironmentStage`
- Cosmic-web classification (filament/void/node membership,
  `Haloes/`-level and `Satellites/Environment/CosmicWebClass`) — no
  cosmic-web classifier (T-web/V-web or similar) exists in the codebase.
- `TidalIndex` — more than one non-equivalent literature convention;
  picking one silently would bake in an unstated definition.

### `ObservabilityStage`
- Anything requiring a survey selection function / instrument model
  (`RubinDetectionProbability`, `RubinCoaddDepth_r`, `CompletenessWeight`,
  `SurveyFootprintFlag`) or a magnitude/surface-brightness (needs
  luminosity from `SharkGalaxyBackend`'s photometry, now available, *plus*
  a `HalfLightRadius` for surface brightness, which still isn't — see
  above) or a mock-sky orientation convention
  (`GalacticLongitude`/`Latitude`, `RA`/`Dec`).

### `HaloPropertiesStage` / `OrbitalPropertiesStage`
- `MassAccretionRateDM` — needs a common time/snapshot grid across the
  tree to differentiate mass vs. time; no shared-grid machinery exists
  yet (each `Epoch` loads independently). `StarFormationHistoryStage`
  built exactly this kind of common-grid machinery for SFH
  (`time_bin_edges`/`rebin_sfh`) — applying the same approach to mass
  would be the natural way to close this.
- Full progenitor-list-dependent quantities are **now available for
  TreeFrog walkable trees and SubFind-HBT trees**:
  - `treeio_treefrog.py` reads the raw file's forward `Head`/`HeadSnap`
    pointers (previously ignored) and inverts them into
    `TreeFrogWalkableData.descendant_lookup`.
  - `treeio_subfind.py` reads the raw file's native SubLink-style
    linked list (`TreeFirstProgenitor`/`TreeNextProgenitor` — also
    previously ignored; a real HBT+ tree file carries these plus
    `TreeDescendant`/`TreeFirstDescendant`/`TreeNextDescendant`, none of
    which this codebase's SubFind reader read before this) — no reverse
    index needed here, the linked list gives every progenitor directly.
    Older/trimmed SubFind-HBT files without these two fields degrade to
    `MergerTreeError` from `get_progenitors_subfind()`, not a silent
    "no progenitors" for every node.
  - Either way, `get_progenitors_treefrog()`/`get_progenitors_subfind()`
    (dispatched via `MergerTreeTools.get_progenitors()`) return every
    progenitor of a node, and `MergerTreeTools.count_mergers()` walks a
    track counting merger-event snapshots
    (`derived.DorchaSpecificStage`'s `NumberOfMergers`, see below).
  - Still **not** available for TreeFrog's non-walkable "full tree"
    flavour (`TreeProgenitor` only ever exposes the single main
    progenitor, no reverse/forward pointer to invert) — a genuine
    missing-infrastructure gap specific to that flavour.
  - No bundled SubFind-HBT test fixture exists yet (a small one is
    planned) — the SubFind-specific tests in
    `tests/test_merger_tree_progenitors.py` use hand-built fixtures for
    unit coverage, plus real-data checks gated on the
    `ANALYSISTOOLS_SUBFIND_TREE_PATH` env var (skipped without it).
- `OrbitalEnergy`/`OrbitalPeriod` (need a host potential model) and
  `TidalTrackClass` (needs a tidal-tracks classification model, e.g.
  Peñarrubia et al. tables) — deliberately left out of
  `OrbitalPropertiesStage.outputs`, see its docstring.

### `SharkGalaxyBackend` / `HydroGalaxyBackend`
- `HydroGalaxyBackend` has no `SharkGalaxyID` equivalent (no SAM-side
  galaxy ID concept for a hydro run) and no photometry path at all (see
  above).
- Any field requiring particle tagging (tracking a *specific* set of star
  particles across snapshots rather than an SPH/FOF re-aggregation each
  epoch) — no particle-tagging infrastructure exists.
- `HalfLightRadius`/`SersicIndex` for both backends — need a spatial
  light/structural profile, not just total luminosity or a fitted image.
- Unit reconciliation against `schema.py`'s declared units — both
  backends return raw values in whatever units the underlying
  `Epoch`/`Dataset` natively provides; no numeric conversion is applied
  anywhere. `validation.SchemaValidator.check()` catches the *labelling*
  mismatch (declared schema units string vs. the source's actual
  `little_h`/`comoving` state) as a warning, but does not convert values.
  Actual unit conversion before write is still unimplemented — the
  natural place would be `WriteStage`, which currently writes columns
  as-is (see its docstring).

### `DorchaSpecificStage`
- `EarliestProgenitorRedshift`, `FossilFraction`, and `NumberOfMergers`
  are implemented. `NumberOfMergers` needs `epoch` (new required
  constructor argument, alongside `reionisation_lookback_time`) and
  computes for TreeFrog walkable trees and SubFind-HBT trees (see the
  full-progenitor-list note above) — left at the `-1` sentinel (matching
  `SnapshotAtMpeak`/`SnapshotInfall`'s existing convention) for
  TreeFrog's non-walkable "full tree" flavour, a SubFind-HBT tree file
  missing the progenitor-list fields, or when the `Epoch` has no tree at
  all.
- Still deferred: `ProgenitorParticleFraction` (needs particle tagging --
  cross-snapshot particle-ID matching against a progenitor's particle set
  at an explicit reference epoch; genuinely new infrastructure, not
  attempted here), `PeakOverdensity` (needs a progenitor density-field
  analysis), `FormationEnvironmentClass` (needs the cosmic-web
  classifier), `MassAccretionRateDM` (needs the common-grid machinery
  noted above) — see the class docstring in `derived.py` for the
  field-by-field mapping.

### Cross-cutting
- **`SatelliteID` stability**: assigned per-build by
  `_concatenate_contexts` (globally, across every `HostJob`), not
  guaranteed stable across independent catalogue rebuilds (e.g. if the
  host/satellite selection or job order changes between runs). No
  persistent ID registry exists.
- **`CatalogueBuilder` doesn't populate Metadata/Cosmology/
  SimulationConfig automatically** beyond `n_satellites`/`n_hosts`/
  `schema_version` (mechanically well-defined from the built context) --
  everything else (`catalogue_version`, `pipeline_git_commit`,
  cosmology parameters, SHARK run config, ...) is real provenance the
  pipeline has no business inventing; set it via the project config's
  optional `metadata: {"Group/field": value}` mapping (see
  `CatalogueBuilder`'s docstring and `configs/dorcha.yaml`).
- **snapshot reader/writer attribute-naming mismatch — now fully fixed**:
  `api/snapshot.py`'s `_RAW_ATTR_ALIASES` maps `gas_Z`/`stellar_Z`/
  `initmass`/`sfr`/`age` to the reader's actual attribute names on read
  (`sfr`/`age` were a second, previously-undiscovered instance of this
  bug — neither ever resolved against real hydro data, only the DMO
  bundled test snapshot masked it, meaning `HydroGalaxyBackend`'s
  age-dependent fields would have silently never populated against a
  real run). `snapio_hdf5.py`'s writer checks the same corrected names,
  and its species-local-indexing bug is also fixed: `_write_metallicities`/
  `_write_star_formation_rates`/`_write_stellar_ages`/
  `_write_stellar_init_mass` previously indexed these species-only arrays
  with a *global* particle-reordering index (correct only when `idx` is
  the identity permutation); a new `write_hdf5._original_ptype()`
  reconstructs the original-row-order type array (the writer is never
  given it directly — see its docstring) so `_species_local_idx` (the
  generalisation of the pre-existing `_gas_local_idx`) works for any
  `idx` permutation/subset, not just the identity case. The SFR write is
  also now gated on `gas_type` rather than `star_type`. Covered by
  `tests/test_snapio_hdf5.py` (a read-then-write round trip with a
  deliberately non-identity `idx`, which would have raised `IndexError`
  or written wrong values under the old code).

None of the deferred-field items above block using the pipeline today —
they can be picked up independently whenever the relevant modelling
decision or infrastructure (particle tagging, cosmic-web classifier,
survey selection function, full progenitor-list tree parsing,
common-grid mass accretion, a structural/light-profile model) is ready.
